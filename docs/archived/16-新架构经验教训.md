# 新架构开发经验教训

## 背景

在将旧架构迁移到新架构（Pydantic + Loguru + PyTorch Lightning）的过程中，发现了一些功能丢失和回归问题。本文档记录这些问题及其解决方案，以避免未来重复犯错。

## 问题 1: 功能丢失 - 绘图功能缺失

### 现象
- 新代码 `run_full_experiment_v2.py` 只保存了 CSV 结果，没有生成任何图表
- 批量实验后无法直接查看结果可视化

### 根本原因
- 过度关注核心训练逻辑的改造
- 忽略了可视化模块的集成
- 没有对照旧代码 `random_repeat_experiment_manager.py` 的功能清单进行验证

### 解决方案
- 在单实验结束后自动调用 `SingleExperimentPlots` 生成图表
- 创建 `BatchExperimentRunnerV2` 类，支持批量实验后的自动聚合和绘图
- 使用 `BatchExperimentPlots` 生成统计图表（置信区间、改进率等）

### 代码示例

# 单实验绘图
try:

### 根本原因
- 开发时只关注单实验的代码改造

## 问题 3: 日志编码问题

### 现象
- Windows 控制台输出中文时出现乱码
- Loguru 在写入特殊字符（如 R²）时抛出 `UnicodeEncodeError`

### 根本原因
- Windows 控制台默认使用 GBK 编码
- Python 的 `print` 和日志处理器默认使用系统编码

### 解决方案
1. 使用 Loguru 替代标准 logging，并配置文件日志为 UTF-8
2. 避免在日志中使用特殊 Unicode 字符（如将 R² 改为 R2）
3. 创建批处理脚本时设置 `chcp 65001` (UTF-8)

### 代码示例
```python
# 使用 RichHandler 解决控制台编码问题
from loguru import logger
from rich.logging import RichHandler

logger.add(
    RichHandler(rich_tracebacks=True),
    format="{message}",
    level=level
)

# 避免特殊字符
logger.info(f"MAE: {mae:.4f}, R2: {r2:.4f}")  # 使用 R2 而非 R²
```

## 问题 4: PyTorch Lightning 的提示信息

### 现象
- 运行时出现大量 Lightning 提示：
  - `💡 Tip: For seamless cloud logging...`
  - `Sanity Checking: ...`
  - `The 'val_dataloader' does not have many workers...`

### 解决方案
1. 设置环境变量 `PYTORCH_LIGHTNING_LOG_LEVEL=ERROR`
2. 在 `LightningTrainer` 中设置 `num_sanity_val_steps=0`
3. 过滤 num_workers 警告

### 代码示例
```python
import warnings
warnings.filterwarnings('ignore', message='.*num_workers.*', category=UserWarning)

# Trainer 配置
self.trainer = pl.Trainer(
    ...
    num_sanity_val_steps=0,  # 禁用 sanity checking
)
```

## 问题 5: Windows 多进程问题

### 现象
- 在 Windows 上使用 `num_workers > 0` 时容易出现：
  - `BrokenPipeError`
  - 死锁
  - 进程卡死

### 解决方案
- Windows 上强制使用 `num_workers=0`
- Linux/Mac 上可以使用更大的值

### 代码示例
```python
import platform
num_workers = 0 if platform.system() == 'Windows' else 4
```

## 问题 7: MIM 训练数据设置错误（严重）

### 现象
- CNN1D-MIM 的 MAE 在缺失率 0.9 时为 0.051
- CNN1D-Baseline 的 MAE 在缺失率 0.9 时为 0.041
- **MIM 表现比 Baseline 差！**

### 根本原因
**MIM 模型训练时只用了单一缺失率（0.5），而不是多个缺失率！**

```python
# 错误代码
if use_mim:
    train_dataset = BatteryDataset(
        data['X_train'], data['y_train'],
        missing_rate=0.5,  # ❌ 只用0.5训练！
        use_mim=True,
        ...
    )
```

正确的 MIM 训练应该使用 `MIMDataset`，在多个缺失率 [0.0, 0.1, ..., 0.9] 上训练。

### 解决方案
```python
from src.data.datasets import MIMDataset, SequenceMIMDataset

if use_mim:
    # MIM模型：使用多个缺失率训练
    train_dataset = MIMDataset(
        data['X_train'], data['y_train'],
        missing_rates=exp_config.training_missing_rates,  # [0.0, 0.1, ..., 0.9]
        use_mim=True,
        base_seed=exp_config.random_seed
    )
else:
    # Baseline：使用完整数据训练
    train_dataset = BatteryDataset(
        data['X_train'], data['y_train'],
        missing_rate=0.0,
        use_mim=False,
        seed=exp_config.random_seed
    )
```

### 教训
1. **核心逻辑必须严格对照旧代码**：MIM 的多缺失率训练是算法核心，不能简化
2. **结果异常时要质疑代码**：MIM 比 Baseline 差是明显的 red flag
3. **单元测试覆盖关键路径**：MIMDataset 的使用应该在单元测试中验证

## 问题 8: XGBoost 维度不匹配错误

### 现象
```
Check failed: ref->Info().num_col_ == n_features (32 vs. 16) : Invalid ref DMatrix, different number of features.
```

### 根本原因
XGBoost 的数据提取逻辑错误：
```python
# 错误代码
X_val = val_dataset.tensors[0].numpy() if hasattr(val_dataset, 'tensors') else val_dataset.X
```

对于 `BatteryDataset`：
- `.X` 返回原始特征（16维）
- 但 MIM 模式需要拼接后的特征（32维）

对于 `MIMDataset`：
- `.X` 返回拼接后的特征（32维）

导致训练集 32 维，验证集 16 维，维度不匹配！

### 解决方案
统一使用遍历 Dataset 的方式获取特征：
```python
if use_mim:
    X_train_list = []
    for x, y in train_dataset:
        X_train_list.append(x.numpy())
    X_train = np.array(X_train_list)
else:
    X_train = train_dataset.X_missing  # 使用处理后的特征
```

### 教训
1. **Dataset 接口一致性**：不同 Dataset 类的内部属性命名要一致
2. **不要依赖内部属性**：优先使用 `__getitem__` 遍历获取数据
3. **XGBoost 需要特殊测试**：树模型与神经网络的数据流不同

## 问题 9: 架构搜索实验的中断恢复

### 现象
- 架构搜索实验运行时间长（34个架构 × 10秒 ≈ 6分钟）
- 中断后需要从头开始运行

### 解决方案
添加 `--start-idx` 参数支持从指定位置恢复：
```python
# 从第10个架构开始运行（跳过前9个）
python run_architecture_search.py --stage coarse --start-idx 10
```

代码修改：
```python
def run(self, start_idx: int = 0) -> pd.DataFrame:
    architectures = self.generate_architectures()
    
    # 支持从指定索引开始
    if start_idx > 0:
        architectures = architectures[start_idx:]
        
    for i, arch in enumerate(architectures, start_idx + 1):
        ...
```

### 教训
1. **长时间实验必须支持中断恢复**：添加检查点或起始索引参数
2. **显示进度信息**：让用户知道当前进度和预计剩余时间
3. **定期保存中间结果**：避免丢失已完成的实验数据

## 最佳实践建议

### 1. 功能迁移检查清单

在重构代码前，先列出旧代码的所有功能：

- [ ] 数据加载
- [ ] 模型训练
- [ ] 模型评估
- [ ] 结果保存
- [ ] 可视化/绘图
- [ ] 批量实验支持
- [ ] 中断恢复
- [ ] 统计分析
- [ ] 日志记录

### 2. 保持向后兼容

- 旧代码在重构期间继续可用
- 新代码使用新的目录结构（`experiments_v2/`）
- 提供迁移指南

### 3. 渐进式迁移

1. 首先确保单实验功能完整
2. 然后添加批量实验支持
3. 最后添加高级功能（如中断恢复、云端同步等）

### 4. 文档同步更新

- 代码修改后同步更新文档
- 记录所有破坏性变更
- 提供使用示例

## 教训总结

| 教训 | 说明 |
|------|------|
| **功能完整性优先** | 不要为了追求新技术而丢失原有功能 |
| **对照检查清单** | 重构前列出所有功能，逐一验证 |
| **渐进式开发** | 分阶段验证，避免一次性大规模改动 |
| **考虑平台差异** | Windows 和 Linux 在编码、多进程等方面有差异 |
| **文档同步** | 代码和文档必须同步更新 |
